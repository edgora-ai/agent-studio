## 结论

**可以接，但要区分两种架构。**

- **A：中央 dsh，仅将 fs/subprocess 远程化。** 源码已提供明确的扩展接口，适合把内置文件、Bash、PTY、LSP 的执行世界搬到远端；**不等于现有工作区选择器、侧边栏和全部第三方插件自动远程化**。
- **B：每个远程 workspace 内运行完整 dsh worker，中心入口切换对应应用。** **这条路线最有利于保留“像本地项目一样”的插件兼容性**：对插件而言，远端 workspace 就是其进程的本地文件系统，Git、监听器、子进程也都在同一环境。但这是多个完整 dsh 实例，**会话、设置、插件状态和侧边栏不会因有了中心入口就自动联邦统一**。

官方文档明确支持通过 Terraform Docker provider，使用 **SSH／TCP 连接远程 Docker 主机**。但这不是“每台机器装个 Agent，就自动成为负载均衡节点”；机器选择、模板和凭据仍需配置。另外，**外部 provisioner 功能标注为 Premium**，选型时需要避开把它当成免费的必备基础。

Coder 还能把工作区中运行的 Web 应用代理出来，这很适合承载远程 `dsh web`。

### OpenSandbox 适合什么情况？

如果你最想要的是：

```text
创建沙箱 → 执行命令 → 操作文件 → 保活／停止／删除
```

并通过一组 SDK/API 接入 dsh，OpenSandbox 更直接。

但如果有多台独立 Linux：
- 可以让它们组成 K8s／k3s 集群，交给集群调度；
- 或者另外做多个后端的路由管理。

## 二、关键发现：只接远程执行 API，现有侧边栏不会自动跟过去

我核对了你当前安装的 `dsh-better-sidebar`：

- 文件树直接调用 Node 文件系统：`profiles/web/node_modules/dsh-better-sidebar/src/fs-tree.ts:19`
- 文件监听直接使用 `fs.watch`：`profiles/web/node_modules/dsh-better-sidebar/src/fs-watch.ts:20`
- Git 直接启动所在机器的 `git`：`profiles/web/node_modules/dsh-better-sidebar/src/git.ts:14`

因此，如果只是：

```text
中央 dsh → 插件 → 云端执行命令
```

就可能出现：

```text
编程工具在云端执行
侧边栏却读取中央机器的文件
Git 操作也在中央机器执行
```

**这不是加一个子代理插件就能解决的。**

dsh 有 `fs`、`subprocess` 等执行能力接口，可以用于远程化；但直接使用宿主文件系统和子进程的插件绕过了这些接口，仍需要适配。当前工作区注册也包含宿主目录检查，不能仅把一个云端路径填进 `cwd` 就完成环境切换。

## 三、两种架构，决定了插件兼容程度

### 方案 A：一个中央 dsh，切换本地／云端执行后端

```text
中央 dsh：统一会话、主代理、界面
         │
    环境路由与执行适配层
         ├─ 本地文件／进程
         ├─ 云工作区 A：文件／进程／终端
         └─ 云工作区 B：文件／进程／终端
```

**这是最严格意义上的“在同一个 dsh 里管理本地项目和云项目”。**

但插件包至少要包含：

1. **环境管理**：列表、创建、启动、停止、状态。
2. **会话绑定**：会话属于哪个环境、哪个项目，不能只有一个路径字符串。
3. **远程文件系统**：读取、编辑、搜索、监听、版本校验。
4. **进程与终端**：流式输出、输入、PTY、取消、退出状态、清理。
5. **界面与插件适配**：项目选择器、侧边栏、Git、文件预览等。

可以把这些打包成一个插件包，但内部是一个完整的**远程执行环境适配层**，不是几次 HTTP 调用。

**优点：**状态更容易集中。  
**代价：**兼容工程最多，不能保证任意第三方插件不改就工作。

### 方案 B：每个环境运行完整 dsh，中心入口切换环境

```text
统一环境入口
├─ 本机项目 → 本机 dsh
├─ 云项目 A → 工作区 A 内的完整 dsh
└─ 云项目 B → 工作区 B 内的完整 dsh
```

**如果你优先要求侧边栏和现有插件尽量照常工作，我更推荐这条。**

因为对于远程 dsh 内的插件来说：
- 项目文件就是本地文件；
- Git 就在同一个环境；
- 文件监听也是本地监听；
- 编程工具、终端、依赖都在同一台“工作机器”里。

中心插件负责选择工作区、启动环境、打开对应 dsh 应用，底层平台负责环境生命周期和访问代理。

但必须明确一个代价：

> **统一入口，不等于统一 dsh 后端。**

各环境的会话、设置、插件状态和侧边栏仍属于各自实例。若要一个全局侧边栏展示所有环境的会话、统一搜索和设置同步，需要再加一层聚合，不能假装现成就有。

**不需要：**
- 每台服务器手工安装 dsh；
- 每台服务器手工安装、升级 code-server；
- 为每个环境管理一个用户访问地址。

**仍然需要：**
- 容器运行时／K8s 节点，或者 VM 基础设施；
- 平台的连接组件；
- 项目环境中的开发工具，以及必要的轻量 helper。

这些应该由模板、镜像和自动部署管理。**远端有执行组件不可避免，但不应该变成你手工维护的 N 套开发平台。**

## “隔离”也必须由环境本身提供

code-server 是编辑器服务，不是隔离机制；Coder 也不会仅凭“创建一个工作区”就自动满足所有安全要求。

项目模板还要明确：

- 哪些项目文件可以挂载；
- HOME、缓存、依赖和凭据是否独立；
- CPU、内存、进程限制；
- 网络和宿主访问权限；
- 停止后保留哪些数据，销毁哪些临时状态；
- 使用普通容器，还是需要独立内核的 VM／microVM。

否则只是把原来共享服务器的问题搬进了一个控制台。

## 因此，方案可以收敛了

**中央 dsh + 集成编辑／搜索面板 + 社区远程执行底座 + Coder 环境管理适配。**

所有功能围绕同一个“项目环境身份”工作，不能出现文件看的是 Host A、Agent 却在 Host B 执行的情况。切换项目时，文件、Git、终端、Agent 执行目标和相关会话一起切换，浏览器地址不需要改变。

前面搭建的本机容器原型，只验证了其中的“隔离执行”部分；**统一项目入口、跨主机环境管理、编辑搜索和移动端体验还没有实现。** 后续应该围绕这个完整目标集成，而不是继续堆叠独立服务器上的 code-server。
