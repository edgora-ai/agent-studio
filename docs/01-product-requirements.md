# 产品需求

版本：v0.4；日期：2026-10-30；状态：实施前草案。v0.3 → v0.4 的变更依据见[设计评审记录](07-design-review.md)。

## 1. 背景与问题

当前工作方式有两个断点：

- code-server 编辑能力完整，但需要在不同机器部署、切换不同地址；移动端通过 IDE 终端操作 Agent 的体验不理想。
- dsh 以会话为中心，更适合移动端；现有侧边栏基本编辑能力可用，但本地文件、远程执行、Git 和项目环境尚未统一绑定。

用户需要的是统一项目工作台，而不是一组服务器书签，也不是每个工作区再部署一套完整 dsh。资源可以分布在不同 Linux 主机或 Kubernetes 节点，用户仍应围绕项目、环境、会话工作。

## 2. 产品定位

Agent Studio 是中央 dsh 的环境管理与远程工作区集成层：

- **会话优先**：通过会话提出任务、观察进度、审批、取消和审阅结果。
- **项目统一**：同一环境身份驱动文件、搜索、编辑、Git、终端和 Agent 工具。
- **中央维护**：dsh、控制台和未来的 code-server 分别只有一个逻辑服务与升级入口。
- **隔离执行**：远程开发进入有明确策略的容器／VM，而非直接使用裸主机的全部权限。
- **渐进增强**：第一阶段保留基本编辑体验，第二阶段联动完整传统 IDE。

首期按单个受信任使用者管理多个环境设计。多租户组织管理、跨用户共享和细粒度团队权限不是首期范围，但服务入口仍必须认证，工作区仍必须校验所属身份。认证、传输与授权的最低规则见 FR-14。

## 3. 部署目标与边界

| 位置 | 允许的组件 | 不要求的组件 |
|---|---|---|
| 中央服务侧 | dsh、Agent Studio 插件／适配层、Coder 控制面、状态与审计存储 | 不把中央进程当作远程项目的执行后备 |
| 远程工作区 | 开发工具、Coder Agent、受版本管理的轻量 helper、语言服务 | 不要求完整 dsh；不要求独立 code-server |
| 基础设施节点 | Docker／containerd／Kubernetes 或 VM 运行基础 | 不要求每台主机维护独立用户 IDE 地址 |
| 第二阶段中央 IDE | 一份 code-server 逻辑服务及受控的远程工作区扩展 | 不以每工作区一个 code-server 替代目标 |

多个独立 Docker 主机的放置策略由明确模板或后续调度能力实现；Kubernetes 路线由集群调度。不能假设 Coder 自动把任意 SSH 主机变成通用调度节点。模板是隔离、资源和实例身份的实际承载者，其交付要求见 FR-13，不能只当作部署细节。

## 4. 范围

### 第一阶段必须具备

- 本地项目与 Coder 远程隔离工作区的发现、选择和明确标识。
- Coder 工作区状态及启动、停止；从受控模板创建环境。产品内重建、销毁和凭据替换入口是待确认的范围扩展；未提供时明确拒绝，平台外部变化仍须被检测并使旧绑定失效。
- 模板契约：隔离与资源策略、允许根目录、每实例身份记录及其版本化维护。
- 同一中央 dsh 的文件、搜索、编辑、Git、终端和 Agent 执行目标一致；PTY 具备可验收的终端语义。
- 不改变本地项目现有行为；远程失败不回退本地执行；绕过绑定路由的本机入口必须被拒绝或禁用。
- 远程环境的资源、文件、凭据、网络和生命周期策略可核查。
- 适配指定版本的现有侧边栏；移动端以会话为主，不依赖终端操作 Agent。
- 可观察的任务状态、可取消执行、失联处理、持久化与恢复验证；受管保存接口防止基于旧版本的覆盖，并披露外部进程直接写入的并发边界。
- 入口认证、传输安全与关键动作的授权规则。

### 第二阶段

从当前项目生成受认证的链接，在同一份中央 code-server 打开对应远程环境、路径和文件，获得传统研发能力。该能力必须先通过可行性验证，不阻塞第一阶段交付。

### 非目标

- 多个完整 dsh worker 的应用入口聚合，即之前的方案 B。
- 第一阶段重写完整 IDE、复制 VS Code 扩展市场或开发通用云平台。
- 静默同步本地和云端代码、自动移动已有会话的执行目标。
- 把 SSH、反向代理或一个目录路径当作隔离机制。
- 未经验证便承诺所有第三方插件透明兼容。
- 自动轮换多个账号、组织级计费、跨集群自动故障迁移。
- 首期在一个会话内向其他绑定委派子任务；子任务必须继承主会话绑定的 ID 与版本，需要另一环境时从对应会话另行发起任务。
- 首期把未安装的打开器、URL scheme 或本机应用当作远程文件的查看方式。

## 5. 功能需求

优先级：P0 为第一阶段必需；P1 为增强；P2 为第二阶段独立能力。

| 编号 | 优先级 | 需求 | 验收要点 |
|---|---|---|---|
| FR-01 | P0 | 单一入口和统一项目环境目录 | 不因切换主机改变 dsh 入口；本地与远程项目均有稳定身份和可见目标标识 |
| FR-02 | P0 | Coder 认证、发现及生命周期 | 能列出有权工作区，启动、停止并观察真实状态；创建仅使用允许的模板；未提供的破坏性动作明确拒绝，外部重建／销毁后旧绑定与审批失效 |
| FR-03 | P0 | 项目／会话／任务显式环境绑定 | 文件、工具和后台任务使用同一绑定；切换界面不改变旧任务的执行位置；实例世代变化使旧核验失效 |
| FR-04 | P0 | 统一文件访问与基本编辑 | 本地与远端均可浏览、读取、保存；保存有版本校验，失败不写到其他环境；并发写入按绑定规则处理 |
| FR-05 | P0 | 统一命令、后台任务与终端 | 命令和 PTY 在目标环境执行；输出、退出、取消及资源清理有可核验事实；PTY 的尺寸、信号、前台进程组与断线恢复按契约验收 |
| FR-06 | P0 | 侧边栏与 Git 只读一致性 | 首期结构化 Git 入口必须支持 status 与 Diff，并在绑定仓库执行；写操作范围按场景文档能力表，不将通用命令冒充侧边栏支持 |
| FR-07 | P0 | 文件名与内容搜索、上下文引用 | 结果带环境、路径、行号；打开和引用不会重新解释成中央主机文件；本机打开器与 URL scheme 不得成为旁路 |
| FR-08 | P0 | 安全策略和凭据边界 | 远端执行满足指定隔离策略；主机控制凭据不交给 Agent；不隐式继承中央密钥 |
| FR-09 | P0 | 断线、状态未知与恢复 | 失联不等于完成或失败；禁止静默本地回退和盲目重复执行副作用；请求重传须通过去重协议验证；恢复窗口与超时语义按声明执行 |
| FR-10 | P0 | 会话优先及移动端连续性 | 手机可提出任务、处理 CLI 运行中的审批／必要澄清、取消及查看文件／Diff；无需终端；发布前须有真实移动设备验收 |
| FR-11 | P0 | 中央状态、审计和持久化 | 会话与环境绑定可恢复；任务事件可查询；敏感值不进入普通日志或模型上下文 |
| FR-12 | P2 | 单份中央 code-server 的项目深链接 | 不新增每主机 IDE；链接正确打开环境和项目，经过认证与绑定授权，有明确的过期与拒绝规则，且执行语义保持远程 |
| FR-13 | P0 | 模板契约与实例身份 | 模板版本化并交付隔离、资源、允许根目录与运行账号策略；每次构建生成可独立登记的实例身份记录；未完成身份核验不开放项目操作 |
| FR-14 | P0 | 入口认证、传输与授权 | 服务入口强制认证与加密传输；关键动作（停止、销毁、审批、跨用户访问）校验主体与工作区归属；失败与越权可观察 |

首期远程结构化 Git 以只读为 P0；暂存、提交、切分支、重置、推送的支持级别及通用命令边界，以场景文档的 Git 能力表为准。本地已有 Git 功能不因该范围而移除。

FR-10 的审批包括编程 CLI 启动后的实际权限请求和必要澄清，不限于“同意启动工具”。不支持会话内交互的 CLI 不能列为首期已支持后端；仅通过模拟手机视口也不能完成移动端发布验收。

环境销毁、重建和凭据替换属于显式破坏性动作；第一阶段必须限制并说明副作用，不允许把“停止”按钮隐式实现为删除项目数据。停止、重建和销毁对绑定、任务与待答请求的级联结果必须可观察，规则见架构文档。自动批量回收不是第一阶段必要能力。

FR-13 的模板不是一次性部署说明：模板版本、期望实例标记、允许根目录与策略版本必须能在项目访问开放前独立取得，并能在重建后重新核验。具体连接与登记步骤见[集成方案](04-integration-plan.md)。

## 6. 非功能要求

| 编号 | 要求 |
|---|---|
| NF-01 | 路由正确性优先：远端不可用、映射删除或绑定失效时拒绝操作，不回退中央主机 |
| NF-02 | 隔离能力由运行策略定义并实测；明确普通容器共享内核，VM 才提供独立内核 |
| NF-03 | 兼容性按 dsh、侧边栏、远程插件、helper、模板／镜像和 Coder 版本组合记录；声明范围不能代替实测 |
| NF-04 | 浏览与输出有分页、大小上限和取消能力；热连接／冷启动分别展示状态，不伪装本地零延迟；已知无法分页的目录必须在兼容矩阵中声明并给出最小上限 |
| NF-05 | 中央服务和 helper 可按声明版本路径升级、校验和回滚；M4 必须实际完成升级及回滚并验证既有绑定、状态库和 helper 可用，不能只给说明；无需逐主机手动安装完整产品 |
| NF-06 | 认证、权限失败、路由失败、连接中断、进程退出、策略拒绝分别可观察，不用一个通用成功状态掩盖 |
| NF-07 | 启动、任务、审批、操作超时与恢复窗口有默认值、配置归属和超时后的状态语义；数值在 M1 实测后确定并记录，不能没有上限地等待 |
| NF-08 | 同一绑定下的并发写入、审批与状态查询有明确规则；受管保存接口拒绝旧版本覆盖，外部进程写入的竞争限制必须披露并分别测试，不承诺任意写入者之间的无覆盖保证；跨绑定结果视为缺陷 |

性能阈值在首个真实跨主机样本后确定并记录，不在没有测量时承诺固定延迟。第一阶段至少记录连接建立、目录读取、搜索首结果、命令首输出、取消完成与断线感知时间。

## 7. 产品完成的定义

完成不是“可以 SSH 登录”或“能创建容器”。必须在同一个 dsh 入口完成：本地项目操作、两个远程环境切换、会话实际执行、文件编辑与搜索、侧边栏 Git、PTY 语义、断线与取消、并发写入保护、隔离边界、入口认证，以及中央重启后的绑定恢复。

范围与验证矩阵见[交付与验收](05-delivery-and-acceptance.md)。场景细节见[核心功能与关键场景](02-features-and-scenarios.md)。
