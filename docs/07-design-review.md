# 设计评审记录：v0.3 → v0.4

评审与复核日期：2026-10-30；对象：v0.3 及其 v0.4 修订草案。本文保留发现与纠偏记录，不是另一份实施规范；现行草案以 01–06 为准。没有安装候选插件、启动 Coder 或完成产品运行验收。

## 1. 评审方法与可信范围

- 主评审通读文档并核查部分外部发布元数据、源码文档及本机安装产物。
- 另一个评审者在未收到主评审结论的情况下通读主文档；其任务明确不核实外部版本事实。主评审随后能看到其报告，所以不能写成“两轮互不可见”。
- 后续复核发现初稿存在推断过度、范围扩大和校验能力表述不准，已在本次 v0.4 修订中纠正。
- 两个评审者都指出某一问题，不是事实已被独立验证两次，更不是运行证据。外部兼容性结论不能借“评审收敛”提高可信度。
- 文档脚本只验证明确编码的结构约束；回归测试、快照哈希与产品功能验收是不同结论。

## 3. 发现及最终处置

保留 D 编号便于对应初稿；严重度用于安排设计工作，不代表已发现运行漏洞。“文档已修订”也不代表对应功能已经实现。

| 编号 | 复核后的判断 | v0.4 处置 |
|---|---|---|
| D-01 | 模板的版本、实例记录来源与交付职责应更明确；不宜说模板承担“全部”安全责任 | FR-13、SC-17 及 Template／InstanceRecord；隔离仍由基础设施执行，认证与路由仍由各层负责 |
| D-02 | **撤回“明确不兼容”“直接安装会失败”**；这不是两轮独立发现 | R-01 恢复“兼容性未知”，M1 在隔离实例测试当前组合，具体错误出现后再选择升级／适配 |
| D-03 | 请求重传与再次执行副作用曾被混淆，不能仅以“重放一次、返回值相同”判安全 | ADR-05 与架构定义去重作用域、参数摘要、原子登记、日志保留及不确定窗口；SC-06 故障注入 |
| D-04 | PTY 的验收覆盖需要补充；v0.3 不是完全没测，已有 M1 输入／取消及 provider 测试 | SC-14 明确尺寸、信号、进程组、游标和清理，不宣称终端是产品相对 IDE 的核心差异 |
| D-05 | 生命周期级联需要闭合，但不意味着必须新增全部破坏性操作入口 | SC-13 验证外部变化及未提供入口的服务端拒绝；产品内重建／销毁／凭据替换列为待确认扩展 |
| D-06 | 实例世代需落实到对象及转换规则；v0.3 已有重建后重新核验原则，并非毫无防护 | 新增绑定版本／会话转换表；派发核对当前认证通道身份，不只比较缓存字段 |
| D-07 | 本机打开器／快捷键是需明确测试的潜在旁路 | 远程模式服务端拒绝或适配；SC-16 验证，不以隐藏按钮代替 |
| D-08 | **撤回“NF 完全不在发布门槛”**；v0.3 已有 NF-05 发布门槛、大小上限与错误分类检查 | 补统一 NF 分配表及编号检查项，要求发布前全部通过；不把原有要求说成不存在 |
| D-09 | 多写入者应分类；初稿把所有进程都要求使用版本令牌，承诺过强 | 受管保存提供版本冲突保护；外部直接写入披露竞争限制，SC-05／SC-15 分别测试 |
| D-10 | 时限配置归属、恢复窗口和窗口外处理需明确 | NF-07；M1 记录实测参数，恢复窗口与去重日志保留期分开；超时未确认清理仍为未知／待确认 |
| D-11 | 内部上下文与公开 cwd 需要可信分类信号，不是靠路径形状判断 | 带外上下文／专用 API；缺少可信信息不解释为内部 anchor |
| D-12 | 认证与绑定授权需要实施细节，但不能推出“手机必定公网”或“同一主体跨设备审批有问题” | FR-14／SC-16；复用现有认证优先，同一有权主体可跨设备一次消费请求；部署变更另行确认 |
| D-13 | 候选文档存在两条执行通道，不意味着产品必须交付两条 | M1 确认实际启用路径，各自验收；未启用路径明确拒绝 |
| D-14 | 大目录限制需在兼容矩阵和容量检查中显式记录 | CK-02 验证阈值、分页／截断、取消与冷热状态；不是 PTY 场景自身覆盖目录测试 |

## 4. v0.4 初稿的修订记录

### 4.1 兼容性推断

初稿把 manifest 未列 rc.4 写成“明确不兼容”，并迫使 M1 在测试前升级或适配。现已撤回：不直接改生产，但允许隔离验证当前组合；失败必须有具体依赖／符号／调用证据。

### 4.2 写入与去重保证

初稿的“所有写入者必须使用版本令牌”“最多一次重放且用户可见结果不变”均不足以作为实现保证。现改为受管／外部写入分类与可验证的去重协议。用户开关不能豁免缺失的安全证明。

### 4.3 草案与既定范围

初稿一边列出待决定事项，一边要求“未决定前按中央草稿实现”，还把独立重建／销毁入口写成 P0。现已分开既定目标、工程建议和范围扩展；未选定建议不等于实施授权。一个项目信任边界也不等于一个目录。

### 4.4 实例变化后的续用

世代字段本身不能说明恢复语义。修订要求：同实例重新认证后可继续原会话；新实例生成新绑定版本和新会话，旧历史只读，不转移旧任务句柄或审批。重建后的旧缓存即使内部相等，也不能绕过当前通道身份核验。

### 4.5 校验能力与评审记录

复核在临时文档副本中证实初稿校验器会放过：重复 NF 映射、把 NF 映射改成“无验证”、把 FR-05 从 P0 改成 P2。修订为：

- FR 场景声明与矩阵逐对双向一致。
- NF 只做单向覆盖分配：必须有唯一映射行，且引用实际定义的 SC／CK；不声称 NF 与场景有双向声明。
- 阶段清单与 FR 优先级一致，第一阶段 P0 不得关联第二阶段专属 SC-11。
- 检查项编号、缺失、重复与非法引用有负向测试；脚本不判断自然语言测试是否充分，也不验证真实模板、安全性或运行兼容。

## 5. 评审来源说明

独立评审报告涉及生命周期、实例世代、anchor、PTY、并发、认证、NF、超时、模板身份来源和第二阶段验收。它未报告插件 rc.4 不兼容，也未联网验证相关事实。初稿将 D-02 标为“收敛”是不准确的，已纠正。

主评审曾在独立评审完成前继续检查部分重叠议题，因此不能严格声称所有条目都具有相互独立的验证过程。本文不再用“两个评审者同意”作为结论成立的证据。

## 6. 范围与后续工作

现行范围与建议见[决策与待验证项](06-decisions-and-risks.md)。技术问题优先通过 M1／M2 查明，不把每项工程选择都变成用户问卷。

- 既定方向保持：中央 dsh、Coder 首期、本地／远程绑定、单项目信任边界、会话优先、第二阶段单份 code-server。
- 草案补充：模板记录、PTY、实例身份转换、认证与容量验收，不新增平台或运行组件。
- 待确认扩展：产品内破坏性管理入口、跨设备草稿同步、新身份服务／公网部署变更；未确认不作为 P0 完成条件。
- 下一步仍是隔离兼容与最小链路实验，不是安装生产插件或迁移已有项目。
